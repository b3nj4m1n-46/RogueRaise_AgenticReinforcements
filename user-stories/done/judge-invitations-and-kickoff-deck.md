# Story: Judge Invitations, Background Form & Kickoff Deck

## Summary

AS a WR Admin
I WANT the judges invited with a personal letter and a form of their own, and a kickoff deck built from what they tell us
SO THAT judges arrive knowing what they're scoring and can be introduced properly, without anyone writing seven emails and a deck by hand

## Acceptance Criteria

- An agent drafts a **personalized invitation per judge** covering the schedule, what's expected of a judge, the evaluative criteria, and an explicit invitation to question the criteria themselves.
- The draft goes through the **same review gate** as every other agent output; nothing is sent until it is approved.
- On send, each judge gets **their own letter and their own magic link**. A judge with a live link is skipped rather than emailed twice, and a letter addressed to someone who isn't a judge on the event is **never sent** — it is reported to staff.
- Delivery is **logged per judge**, so "did Ada get hers?" is answerable.
- `/judge/background/[eventId]` is **magic-link gated**, collects name, title, bio, expertise, and how they'd like to be introduced, and stores it on the `Judge` record.
- A **question about the criteria** routes to WR Admin **and** the sponsor POC, with reply-to pointing back at the judge. An unchanged question on a re-save doesn't notify twice.
- The **kickoff deck** agent produces a real, brand-themed `.pptx` covering the topic, the sponsor, their pain and needs, the opportunities, the criteria, the judges (using background-form data), the schedule, and the location.
- The deck is **downloadable by WR Admin** and regenerated by re-running the agent; older versions stay downloadable.
- A deck is **always produceable** — with no AI provider, no confirmed weekend, no criteria, and no judges.

## Implementation Plan

`access/redeem.ts` generalizes magic-link redemption (the judge form is its second caller; `intake/access.ts` delegates). `judges/*` holds access, schema, emails, the send service, and the background-form action. Two agent handlers join the registry. `decks/content.ts` builds slides purely; `decks/render.ts` renders them to `.pptx` with pptxgenjs.

## Review

Verified in the browser and the database: the judge agent drafts and refuses without judges or criteria; sending a draft with no per-judge markers is refused with an actionable message; a real 8-slide 95 KB `.pptx` downloads with the correct content type. 25 new tests cover per-judge letter splitting, send idempotency, unmatched addresses, token scoping across events and roles, criteria-question routing, and deck content under every missing-data combination.

**Gap the browser exposed:** the judge agent's trigger statuses skipped `repo_review`, so drafting invitations was blocked in the middle of the flow for no reason. Its statuses are now contiguous from `intake_complete`.

**Known gaps (deliberate):** the deck has no headshots (the background form doesn't upload one yet — the `Judge.headshot_blob_url` column is there for it); delivery status is audit rows rather than provider-level receipts, which needs the real Resend adapter; and the invitation quality is unverifiable while the dev provider is the only one configured.

## Learnings

- Extracting `redeemMagicToken` when the *second* caller arrived — not when the first was written — put the shared security check in one place at exactly the moment it became shared. The intake's 92 tests passing unchanged is what made the refactor safe to do mid-flight.
- The `## JUDGE: <email>` marker is the third use of "split agent output on a marker the prompt explicitly demands". It has earned being a house pattern: split on structure the model was merely *expected* to produce and you get nonsense the first time it doesn't.
- Refusing to send a letter to an address that isn't a judge on the event turned an invisible failure (an agent inventing a recipient) into a reported one. That check cost four lines.
- Making the deck's structure deterministic and the model's contribution one slide means the deck is never blocked on the model. For an artifact with a hard deadline — Friday, 5:00 PM — that tradeoff is obviously right, and it wouldn't have been obvious if the deck had been specified as "ask the model for a deck".
- Carry-forward for **M6**: the marketing agents (outreach, social, landing page) are three more handlers on the same machinery, and the landing page content feeds Phase 2's public event page. The `admin_and_sponsor` review gate on outreach has the same missing-surface problem as `admin_and_stakeholders` — that external review view is now owed by three gates.
